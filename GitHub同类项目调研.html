别人是怎么做「软件时长统计」的 对照 6 个开源项目，看你这个工具处在什么位置、哪些地方值得学

调研对象：时间统计 TimeStats v1.0.0 · 2026-10-31
  1. 这个方向 GitHub 上确实有同类项目，但绝大多数比你做的简单。你手里的「跨天拆分 + 睡眠扣除 + 启动器交接」三件事，翻遍这几个仓库没人做全——这不是客套，是它们的 README 里自己承认的短板。
  2. 最值得抄的不是功能，是两个工程细节：怎么判断"这游戏真的在跑"、怎么在崩溃后不丢数据。这两块别人踩过的坑比你多。
  3. 你真正缺的功能只有一个：人不在电脑前时，时间照算。而这个改动小到只需要几行代码——因为你已经用着能解决它的那个系统能力了。

一、找到了哪些项目

按「跟你重合度」从高到低排。重合度 = 定位是不是"给非 Steam 的游戏/软件记时长"。

二、三个值得细看的项目

2.1 playtime-windows —— 定位最像，工程细节最值得抄

它怎么判断"游戏还在跑"

C# / WPF · MIT · 2026 年 9 月首发，v0.1.1

你用的是每 3 秒跑一次 tasklist 命令，把结果解析出来找进程名。它是两套并用：

正常情况
向 Windows 订阅「有进程启动 / 有进程退出」的事件通知（WMI 的 Win32_ProcessStartTrace）。平时程序在睡觉，只有事件来了才醒。所以它发现游戏启动比你快——你的最坏情况要等 3 秒。
兜底
订阅失败（权限不够、系统精简过、WMI 坏了）就自动退回轮询，不报错、不崩溃，只是退化成你现在的方式。
省电
开着事件通知、又没有任何游戏在计时时，轮询间隔从 3 秒放宽到 15 秒；一旦开始计时，收紧回 3 秒。

它防三个坑的办法

防同名
不只看进程名，还要求 exe 的完整路径必须在你配置的安装目录下（用 QueryFullProcessImageName 拿真实路径）。因为一堆游戏的进程都叫 game.exe、launcher.exe，只比名字必然误判。
防 PID 复用
用「进程号 + 进程启动时刻」拼成唯一身份证（pid:启动时刻）。进程号会被系统回收再分配，加上启动时刻就不会认错人。
防虚增
如果两次检查之间隔了 20 秒以上（系统卡死、休眠、时钟跳变），直接把当前会话判为 中断 结账，不把这段糊涂时间算进去。

它怎么做到崩溃不丢数据

思路和你很像，但更极致：

立即落盘
新会话一建立就马上写一个文件到 active/ 目录，不是等退出才写。
心跳
每 5 秒更新这个文件的 lastHeartbeat 字段。
自愈
下次启动时扫 active/，发现残留文件 → 说明上次是被强杀 / 崩了 → 以 最后一次心跳 当结束时间，标成 interrupted 归档。宁可少算几秒，绝不多算。
它自己承认的短板，恰好是你的长处：「只测进程运行时间，包含挂机和后台时间」；没有跨天拆分；没有睡眠扣除。这三条你的 README 里都有，而且实现得比它细。

2.2 GameTracker —— 功能最全，两个机制设计得最巧

「分层解析」：猜这个 exe 是哪个游戏

Python + Flet · AGPL-3.0

你现在的做法是：用户加软件时手动填一个主进程名，抓不到就手动补「关联进程名」。它是自动逐层猜，猜不到才问人：

第 1 层
查老账：这个 exe 路径我以前见过吗？见过就直接认。（watcher_process_map）
第 2 层
查商店清单：读 Steam 的 appmanifest_*.acf、Epic 的 *.item 清单、GOG 注册表，看这个安装目录对应哪个游戏。这一步能白捡整个游戏库。
第 3 层
模糊匹配：拿 exe 名/目录名跟你库里的名字、IGDB 别名做相似度打分，低于 85 分不算数。
第 4 层
问用户：弹一个通知"这是 XX 吗？"，你点"是"，它就记住这条映射，下次不用再问。

「去抖 + 兄弟交接」：专治启动器

10 秒去抖
进程必须活过 10 秒才认为"这是真游戏"，天然把一闪而过的启动器过滤掉。比你现在靠「活了多久」判断更直接。
15 秒交接
计时中的进程消失后，等 15 秒，看同一个安装目录下有没有新进程顶上来。有 → 无缝接着算，不产生两条记录。
对照你
你的做法是"启动器快速退出（launcherQuickExitMs 内）+ 候选名单里有别的进程在跑"就进 HANDOVER 状态，窗口 2 分钟。逻辑更明确，但候选名单要用户手填——这是它比你聪明的地方。

两个"体感"功能

记错能改
统计错了会弹通知"正在统计 XX"，点「不对」可以就地改名——已经累计的时间保留，只是换个标题，不用重新开始。
诊断日志
每次判断都写日志，能回答"我这个游戏为什么没被统计到"。日志里会写清楚是被哪个过滤器拦下的、哪一层匹配上的、模糊分多少。

2.3 ActivityWatch —— 架构层面的另一种答案

它不相信"开始 / 结束"，它只记"心跳"

19.4k star · 跨平台 · MPL-2.0

你的模型是「一次会话 = 开始时间 + 结束时间」，一行记录。它的模型是：

采集器
每隔几秒发一次"现在是 Chrome 在前台，标题是 XX"，这叫心跳。
服务端
把连续的心跳拼成时间段。中间断了就自然断开，不需要谁去"关闭"它。
好处
程序崩了最多丢最后几秒；不需要维护"开始/结束"这种脆弱的状态机；多个采集器可以同时跑、各自记各自的。
AFK 采集器
单独一个小进程，专门只干一件事：判断你有没有在动键盘鼠标。主采集器再根据它来决定这段时间算不算数。
要不要改成心跳模型？ 不建议。你的"会话"模型更适合"玩了这个游戏多久"这个业务——用户要看的是"今天玩了 3 小时 20 分"，不是一堆心跳点。它的模型适合"我一天的时间去哪了"这种流水账。盲目照搬会把简单问题复杂化。

三、能借鉴什么（按性价比排序）

1. 空闲扣除 —— 人不在，别算了

★★★★★ · 改动量：小

参考：GameTracker 的 idle pause（默认 10 分钟无输入就暂停）、ActivityWatch 的 AFK 采集器。

现在的问题
游戏开着去吃饭、去睡觉忘了关，这几个小时全算成"游玩时长"。这是所有同类项目都被吐槽的第一个点，playtime-windows 干脆在 README 里写明了不管。
好消息
你的程序已经在用 Electron 的电源监听（powerMonitor 的 suspend / lock-screen），而同一个对象上就有一个现成方法 getSystemIdleTime()——直接返回系统闲置了多少秒（基于键鼠输入），不用装任何第三方库，不用调任何 Windows 命令。
怎么改
在 tick() 里读一次闲置秒数，超过阈值（建议默认 5 分钟）就把这段时间累加进 r.gapMs。你的 gapMs 字段和"睡眠扣除"已经在用同一套逻辑了，等于只是多接一个来源，统计口径完全不用动。
要注意
别把"暂停"做成"结束"——用来看视频的游戏挂机应该继续算。做成一个可开关的设置项，默认值要保守（比如 10 分钟），并且像 GameTracker 那样"一有输入立刻恢复"。

2. 自动读 Steam / Epic 游戏库

★★★★☆ · 改动量：中

参考：GameTracker 的第 2 层、Gameplay Time Tracker 的启动器集成。

为什么值
你现在必须手动点「＋新建」→ 找到 exe → 选中。对小白来说这一步劝退率最高——"游戏在哪我都不知道"。如果能一键扫描出"你装了 47 个游戏，要统计哪些？"，上手门槛直接归零。
怎么做
Steam 的是纯文本文件，不难解析：读 steamapps/libraryfolders.vdf 找到所有库目录 → 读每个 appmanifest_*.acf 拿游戏名和安装目录 → 在目录里找体积最大的 .exe 候选。图标同样能从 Steam 的缓存里拿。
顺带解决
自动发现的同时，把整个安装目录记下来——以后判断"这个游戏在跑"就可以用「路径前缀」而不是「进程名」，同名 exe 的问题一起解决（见第 5 条）。

3. 「为什么没统计到」的诊断日志

★★★★☆ · 改动量：小

参考：GameTracker 的 watcher.log，带级别、带轮转、能按模块 grep。

为什么值
这个功能不是给用户看的，是给你自己看的。现在有用户说"我玩了 2 小时没记上"，你只能猜：是进程没扫到？是名字不对？是交接失败了？是一开始就在跑所以被基线跳过了？
怎么做
设置里加一个「诊断模式」开关。打开后每次 tick 往 data/debug.log 写一行：扫到多少进程、每个在监视的软件判定结果是什么、为什么跳过。出问题时让用户开一下、玩一次、把日志发你。
附带好处
你现在有 scripts/probe.js 检查进程扫描，这是"开发时能查"。日志是"用户现场能查"，两者不重复。

4. 记错了能就地改名

★★★☆☆ · 改动量：小

参考：GameTracker 的「Wrong game?」——选中正确条目后，已累计的时长保留，只换标题，不用重开。

场景
两个游戏的进程名撞了，或者用户把"启动器"错加成了"游戏本体"，导致时长记到了错误的卡片上。
怎么做
详情页的某条记录旁边加「记错软件了」，弹出库列表选正确的，改这条记录的 appId 即可。你的 sessions.ndjson 是只追加的，删单条时才重写——这个操作正好走同一条重写路径。

5. 用「路径前缀」辅助校验同名进程

★★★☆☆ · 改动量：中

参考：playtime-windows 的 Matches()——进程名对了还不够，exe 路径必须在配置的目录下。

风险
你目前只按进程名匹配（snap.byName）。如果用户库里有两个都叫 game.exe 的游戏，或者某个游戏和某个系统工具同名，会互相干扰。
为什么只给三星
你的场景里这个概率不高，而且加严校验会带来新问题：有些游戏会从临时目录、更新器目录启动，路径对不上反而漏记。建议做成"宽松模式默认开、严格模式可选"，别一上来就卡死。

6. 分层轮询省电

★★★☆☆ · 改动量：小

参考：playtime-windows 的 3 秒 / 15 秒双档。

现状
你是 pollActiveMs: 3000（有会话时）、pollWatchMs: 5000（开自动监视时）。也就是说开了自动监视，一天要跑 17280 次 tasklist，每次启动一个进程、解析 CSV。
怎么改
三档：没有会话 + 没有自动监视 → 不轮询（你现在已经是这样）；自动监视但没在计时 → 15 秒；正在计时 → 3 秒。代价是"游戏启动后最多 15 秒才被记录"，但这个误差可以用「开始时间往前推半个周期」补回来——你已经在这么做了（startedMs = now - pollActiveMs / 2）。

7. 两次检查间隔过大 → 判中断

★★☆☆☆ · 改动量：极小

参考：playtime-windows 的「now - lastTick > 20 秒就 FinishAll("interrupted")」。

场景
电脑卡死、系统时间被改、休眠唤醒异常，导致两次 tick 之间隔了很久。这时候你把它当成"一直在跑"就会凭空多算几小时。
怎么改
你已经有 maxSessionMs 兜底（单次最多 24 小时），但那是很粗的一道闸。加一条：tick 间隔超过某个阈值（比如 60 秒）就把这段计入 gapMs，不进有效时长。

8. 年度热力图

★★☆☆☆ · 改动量：中

参考：GameTracker 的 GitHub 风格热力图、Steam Wrapped 的年度总结。

为什么值
你的图表已经能看按天/周/月。但"一年 365 格、每格深浅代表玩了多久"这种图传播性极强——用户会截图发出去，等于免费宣传。而且数据你全有。
备注
这类功能是"锦上添花"，不是"雪中送炭"。先把 1、2、3 做完再说。

四、明确不建议学的

这些功能在别人的项目里看着很香，但对你的定位是减分项：

  • 云同步 / 账号体系 —— 你的核心卖点是"拷走就能换电脑，删掉就等于没发生过"。加上账号，这个卖点立刻消失，还要处理备案、隐私政策、服务器成本。
  • 成就系统 / 社交动态 / 好友排行 —— 需要后端，且和你"不联网"的承诺直接冲突。
  • IGDB 封面墙 / 游戏元数据 —— GameTracker 做得很好看，但要走 API、要 key、要联网。你现在从 exe 里提图标（256px→32px→首字母）已经够用，且完全离线。
  • Discord Rich Presence —— 同上，要联网。而且真正用的人很少。
  • 全屏浮层提醒 —— Game Time Manager 的做法，用来防沉迷。实现要在游戏画面上叠一层，容易和反作弊打架、容易崩，收益和风险完全不成比例。
  • 存档备份 —— Gameplay Time Tracker 的差异化功能，但那是另一个产品的事，和"计时"没因果关系。

五、如果只做三件事

01
空闲扣除
用 powerMonitor.getSystemIdleTime()，接到已有的 gapMs 上。改动最小、体感提升最大，直接解决"挂机算时长"这个所有同类产品的头号槽点。
02
自动读 Steam 库
让用户不用再手动找 exe。这一步决定"新用户第一次打开能不能在 30 秒内看到成果"，是从"能用"到"好用"的分水岭。
03
诊断日志
不增加用户可见的功能，但能让你从"猜哪里出问题"变成"看日志就知道"。这是你一个人维护这个项目时最省命的东西。

附：一个顺手能修的隐患

PID 复用会让"已经退出的游戏"被误判为还在运行

位置
tracker.js 的 _alive()：先看 r.pid 在不在当前进程号集合里，在就认为还活着。
问题
Windows 的进程号会被回收再分配。如果游戏退出后，系统恰好把同一个号分给了别的进程，snap.byPid.has(pid) 仍然为真 → 计时不会停，直到那个进程也退出。
概率
很低，但一旦碰上就是"凭空多记几小时"，用户会觉得数据不可信。playtime-windows 用「进程号 + 启动时刻」做唯一键根治了它。
改法
启动时把进程的启动时刻一起存下来，判活时除了号还要对得上启动时刻。或者更省事：把 byPid 从"号集合"改成"号 → 进程名"的映射，判活时连名字一起校验。
